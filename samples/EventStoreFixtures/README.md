# EventStoreFixtures

Writes an event store **through dotnetcqrs's real write path**, for anything that needs a store
written by dotnetcqrs itself: the `eventstore-viewer`'s tests, the `events-read` contract probe in
`cqrs-system-contracts`, demos. It is a fixture generator, not a host.

It dispatches commands through `DeciderRegistry`, the call `MapCqrsGateway` makes, so events are stored
exactly as a host stores them (envelope, metadata, `created`). It uses the `order` and `task` deciders of
`samples/OrderFulfillment`, plus a `customer` aggregate with personal data, which is the smallest thing
that makes the stack write `{"$pii":{"s":subject,"c":ciphertext}}` envelopes: `Pii<string>` event fields
and a registered `IPiiProtector` that encrypts them under the stream's own subject. Plaintext goes in;
only the envelope is stored.

## Run

```
# SQLite (deletes and recreates the file and its -wal/-shm)
dotnet run --project samples/EventStoreFixtures -- --sqlite path/to/events.db

# Postgres (the role must be able to create the events table)
dotnet run --project samples/EventStoreFixtures -- \
    --postgres "Host=127.0.0.1;Port=5432;Database=events;Username=postgres;Password=..."

# both stores in one run, from the same scenario
```

The scenario is fixed: 34 commands, 30 events across 20 streams, and 4 commands the stack must
**reject** (no events are written for them). The program fails if a command that should have been
rejected is accepted, or the other way round, so a change in the stack cannot silently ship a wrong fixture.

Event ids and timestamps are generated by the stack, so two runs differ in those. The data, including the
ciphertext, is deterministic.

## The KMS is not real

Personal data goes through `InMemoryKmsClient`, whose "ciphertext" is `inmem:{subject}:{base64 plaintext}`:
reversible, not encryption. That is fine for synthetic fixtures (which is all this writes) and is the
point of that class, but **never register it in a real host**.
